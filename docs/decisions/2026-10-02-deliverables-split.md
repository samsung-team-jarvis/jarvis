# Decision: 작업물 4개 분할과 담당

## Status
- Accepted — 일부 작업의 담당 이동: [2026-10-04 작업 재분배](./2026-10-04-task-rebalance.md)

## Date
- 2026-10-02

## Context
- 수행계획서의 역할은 기술 종류별(NPU 경량화 / STT·YOLO / State Machine / ESP32)이었다. "NPU 경량화"는 모든 모델에 걸치는 일이라 혼자 맡으면 다른 사람의 모델을 기다리게 되고, 결과물의 책임자가 흐려진다.
- 팀원마다 코딩 경험이 다르다. 신지호는 코딩 경험이 적다.
- 과목 평가와 개인 포트폴리오 모두 "누가 무엇을 만들어 어떤 수치를 냈는가"가 드러나야 한다.

## Options
- Option A: 수행계획서 역할 그대로 (기술 종류별)
- Option B: 입력 → 출력이 분명한 작업물 4개로 나누고, 각자 데이터 → 모델/코드 → 보드 → 측정까지 끝까지 맡는다

## Decision
- 선택한 안: B (팀 내 결정권자 이현종 결정)

| 작업물 | 담당 | 입력 → 출력 |
|---|---|---|
| ① 비전 데이터·모델 + 보드 + 팀 운영 | 신지호 | 카메라 → `.rknn` 비전 모델 |
| ② 음성 → 명령 AI 서비스 + 공통 런타임 | 이현종 | 음성 → Function Call JSON / 서비스 실행 기반 |
| ③ 상황 인식 + 안전 | 최지환 | 음성·비전·센서 → 상태·위험 판단·차단 명령 |
| ④ 제어 하드웨어 + 모형 | 최석진 | 제어 명령 → 장치 동작 / 센서 → 측정값 |

- 선택 이유:
  - 작업물 경계가 [interfaces](../architecture/interfaces.md)의 토픽과 같아서 병렬 개발이 쉽다.
  - 작업물마다 [METRICS](../METRICS.md)의 대표 지표가 있어 개인 기여가 수치로 드러난다.
  - ①은 코딩 경험이 적은 팀원을 고려해 **GUI 도구·노트북 실행·recipe 실행 중심**으로 구성하고, 필요한 노트북·스크립트·서비스 코드는 ②가 만든다 (VIS-08, VIS-10, BOARD-06, BOARD-08).
  - 규칙 파서(FUS-02·06)는 LLM의 비교 기준선이자 대체 경로라서 ②로 옮겼다 ([규칙 파서 결정](./2026-10-01-rule-parser-baseline.md)).
  - 사용자 화면 출력(대시보드)은 설계에 비어 있던 부분이라 ②의 선택 과제(UI-01·02)로 추가했다. Gate 4 이후에만 착수한다.

## Consequences
- 장점: 책임 소재 명확, 병렬 개발, 개인 성과의 수치화
- 단점: ②의 작업량이 가장 많다 → 대시보드는 선택 과제로 두고, STT는 기성 모델(sherpa-onnx)을 쓴다. ①이 ②의 노트북·스크립트에 의존한다 → VIS-10을 VIS-06보다 먼저 끝낸다.
- 영향을 받는 문서: [PLAN](../PLAN.md) 작업물 표·담당, [git convention](../conventions/git.md) scope(`dashboard`), labeler(UI 라벨), [onboarding](../onboarding.md)

## Verification
- PLAN의 모든 작업 항목에 담당이 지정됨 (공동 항목 포함)

## Revisit
- 특정 작업물이 다른 작업물보다 크게 늦어지면 (Gate 기준) 작업 재배분
- ①의 팀원이 코딩 작업을 원하면 VIS-08(`vision_svc`)을 ①로 되돌린다
