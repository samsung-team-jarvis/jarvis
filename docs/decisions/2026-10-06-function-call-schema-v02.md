# Decision: Function Call 스키마 v0.2 (장치 8종 · 세기 통일 · 결제)

## Status
- Accepted ([v0.1](./2026-10-02-function-call-schema.md)을 넓힌다 — 기존 이름·번호는 그대로. [open-questions](./open-questions.md) Q-14 답)

## Date
- 2026-10-06 (내용은 2026-10-05에 결정권자가 확정)

## Context
- 시연 환경을 가상 주방으로 바꾸면서 장치를 8종으로 넓히기로 했다 ([decision](./2026-10-05-virtual-kitchen-demo.md)). 등록된 프로젝트명("스마트 자영업 서비스 어시스턴스")에 맞게 매장 장치와 결제가 들어간다.
- v0.1은 장치 3종(후드, 화구 2개)과 Action 10개다. 규칙 파서, 응답 문장, LLM 데이터 v1, 기준선이 모두 이 범위다.
- 명령 해석은 작은 모델(0.6B~2B)이 한다. 2026-10-05 Mac 시험 학습에서 값의 종류가 고르지 않으면 그대로 약점이 되는 것을 봤다 (되묻기 데이터의 75%가 한 종류 → 되묻기를 거의 못 함. 저장소 밖 실험이라 METRICS에는 없다).
- 결제는 되돌리기 어렵다. 음성 인식은 숫자를 자주 틀린다 (spk01 val: "3분" → "산 분").

## Options
- 장치의 값: (A) 모든 장치 세기 1~3으로 통일 / (B) 장치마다 다른 값 (에어컨 온도 18~30, 조명 밝기 0~100, 음량 0~10)
- 결제 금액: (A) 말로 받지 않고 가상 결제 단말의 금액을 쓴다 / (B) "만 이천 원 결제해 줘"처럼 금액을 말로 받는다
- 확인: (A) "네"·"아니요"를 Action으로 둔다 / (B) 확인 대답은 LLM을 거치지 않고 키워드로만 처리한다
- 환풍기: (A) 후드와 같은 장치 / (B) 별도 장치

## Decision
- 선택한 안: 모두 **A** (결정: 이현종)

| 항목 | 결정 |
|---|---|
| target 추가 | `fryer`(튀김기), `light`(조명), `aircon`(에어컨), `fan`(선풍기), `music`(음악) |
| 환풍기 | 후드와 같은 장치 (`hood`를 부르는 다른 말) |
| 세기 | 모든 장치 1~3. 조명은 밝기, 음악은 음량으로 읽는다. 에어컨 온도를 숫자로 받지 않는다 |
| 타이머 | 가열 장치(화구·튀김기)와 후드, 전체에만 |
| Action 추가 | 11 `CHECK_AMOUNT`(금액 확인), 12 `REQUEST_PAYMENT`(결제 요청), 13 `CONFIRM`(네), 14 `DENY`(아니요). 모두 인자가 없다 |
| 결제 | 금액은 가상 결제 단말의 현재 금액. 결제 요청은 Safety Guard가 항상 확인(`ASK`)을 받은 뒤 실행 |

- 선택 이유:
  - 세기 통일: 값의 종류가 장치마다 다르면 데이터가 늘고 작은 모델이 헷갈린다. 켜기·끄기·세기·타이머·상태 확인은 지금 Action에 target만 늘리면 된다.
  - 금액을 말로 받지 않음: 숫자를 잘못 들어 틀린 금액을 결제하는 일을 구조적으로 없앤다. 결제 명령에 인자가 없어 모델이 지어낼 값도 없다.
  - 확인을 Action으로: 음성 → 명령 경로를 하나로 유지한다. 기다리는 질문이 있는지는 Safety Guard가 판단한다 ([LLM은 말 그대로, 판단은 Guard](./2026-10-02-llm-literal-guard-decides.md)).
  - 번호 1~10과 기존 target 이름을 바꾸지 않아 데이터 v1과 v0.1 코드가 그대로 유효하다.

## Consequences
- 장점: 스키마가 넓어졌지만 규칙은 늘지 않았다 (세기 한 종류, 결제는 인자 없음).
- 단점:
  - "에어컨 24도로" 같은 말은 지원하지 않는다 (세기로 되묻거나 지원 외).
  - `all`이 조명·음악까지 포함한다. "다 꺼 줘"가 매장 조명도 끈다 — 써 보고 가열 장치만 끄는 표현을 따로 둘지 본다.
  - **데이터 v1의 일부 정답이 v0.2와 어긋난다**: "조명 켜줘"·"에어컨 꺼줘"·"볼륨 줄여 줘" 등 22문장이 `UNSUPPORTED`다. 데이터 v2(LLM-14)에서 고친다. 그때까지 v1으로 잰 규칙 파서 수치는 낮게 나온다.
  - 규칙 파서의 판단이 바뀐 곳: "음악 멈춰"·"선풍기 정지"는 긴급 정지가 아니라 그 장치 끄기, 문장 맨 앞의 "계산"만 결제.
- 영향: [interfaces](../architecture/interfaces.md) §2.2·§3·§5, `common/function_call.py`, `services/llm_svc/rule_parser.py`, `services/audio_svc/responses.py`, `common/kitchen_link.py`(가열 장치에 튀김기), `data/stt/script.csv`(s34 "노래 틀어줘"의 정답), PLAN LLM-14

- "다 꺼 줘"로 조명까지 꺼지는 것이 시연에서 문제가 될 때
- 결제 확인 흐름(FUS-03)을 만들면서 `CONFIRM`·`DENY`만으로 부족할 때
