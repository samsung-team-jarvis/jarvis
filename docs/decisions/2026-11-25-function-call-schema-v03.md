# Decision: Function Call 스키마 v0.3 (오븐 2개 · 전자레인지 · 후드 2개)

## Status
- Proposed — 사용자(가상 주방 담당 최석진) 제안. LLM 담당(이현종)·상황 인식·안전 담당(최지환) 합의 후 Accepted ([v0.2](./2026-10-06-function-call-schema-v02.md)를 넓힌다)

## Date
- 2026-11-25

## Context
- 가상 주방(Unity)에는 오븐 2개, 전자레인지, 후드 2개(튀김기 위·화구 위)가 있다. v0.2의 장치는 `hood` 하나와 가열 장치 3개(`burner_1`·`burner_2`·`fryer`)뿐이라, 나머지는 말로 제어하지도 안전 감시하지도 못한다.
- 장치 이름은 음성 명령 전 경로가 같이 쓴다: LLM 출력 → Safety Guard → `kitchen/cmd` → Unity, 그리고 상황 인식(`fusion_svc`)·자동 차단·응답 문장·시뮬레이터의 가열 장치 목록.
- LLM은 학습한 target만 낸다. 스키마에 없는 이름을 내면 검증에 실패해 규칙 파서로 대체되고, LLM이 `UNSUPPORTED`를 내도 규칙 파서가 동작과 장치를 분명히 찾으면 규칙을 따른다 (`interpret.resolve`, #STT-14). 그래서 재학습 전에도 규칙 파서로 새 장치를 다룰 수 있다.
- 보드 시연(2026-11-25)에서 "후드 켜 줘"는 자주 쓰는 말이었다.

## Options
- 오븐·전자레인지: (A) 가열 장치 — 온도·과열 경고·방치 판단·자동 차단 대상 / (B) 일반 장치 — 켜고 끄기만
- "후드"만 말했을 때: (A) 어느 후드인지 되묻는다 / (B) 두 후드를 함께 켜고 끈다 / (C) 후드를 나누지 않는다
- 기존 `hood`: (A) `hood_fryer`·`hood_burner`로 바꾸고 `hood`는 없앤다 / (B) `hood`를 "둘 다"로 남긴다

## Decision (제안)
- 오븐·전자레인지 **A (가열 장치)**, "후드"만 말하면 **A (되묻기)**, 기존 `hood` **A (없앰)** — 사용자 결정, 합의 대기

| 항목 | 제안 |
|---|---|
| target 추가 | `oven_1`(1번 오븐), `oven_2`(2번 오븐), `microwave`(전자레인지), `hood_fryer`(튀김기 후드), `hood_burner`(화구 후드) |
| target 제거 | `hood` — "후드"·"환풍기"만 말하면 화구("화구"만 말함 → 번호 되묻기)처럼 `ASK_CLARIFY`(target 없음) |
| 가열 장치 (`HEATERS`) | `burner_1`·`burner_2`·`fryer` + `oven_1`·`oven_2`·`microwave` |
| 세기 | 모든 장치 1~3 그대로 |
| 타이머 | 가열 장치 6개, 후드 2개, 전체 |
| 가상 온도 | 새 가열 장치도 §4.5의 같은 규칙(세기 → 목표 120·180·270°C, 265°C 자체 차단)을 쓴다 — 시연용 단순화 |
| Action | 바뀌지 않는다 (번호 1~14 그대로) |

- 선택 이유:
  - 가열 장치로 보면 "오븐 켜 두고 자리 비움"도 방치·자동 차단 대상이 된다. 이 프로젝트가 막으려는 사고의 범위와 맞다.
  - 되묻기: 두 후드를 몰래 함께 켜는 것보다, 어느 장치를 움직이는지 사용자가 알게 하는 편이 낫다. 화구 번호를 되묻는 방식과 같다.
  - Action 번호와 함수 토큰 형식은 그대로라 데이터 형식과 파서 구조는 바뀌지 않는다.

## Consequences
- **LLM 재학습이 필요하다.** 학습 데이터의 `hood` 사례(후드 켜기·끄기·세기·타이머)를 두 후드와 되묻기로 바꾸고, 오븐·전자레인지 사례를 더한다. 재학습 전에는:
  - LLM이 `hood`를 내면 스키마 검증에 실패 → 규칙 파서 (튀김기 후드 / 화구 후드 / 되묻기)
  - 오븐·전자레인지를 `UNSUPPORTED`로 내면 규칙 파서가 동작·장치를 찾을 때 규칙을 따른다
  - 응답이 규칙 파서 경로라 LLM 기준선·측정(METRICS)과 비교할 수 없다
- 규칙 파서는 "튀김기 후드"를 튀김기로, "화구 후드"를 화구로 읽지 않게 **후드를 장치 이름보다 먼저** 봐야 한다.
- 가열 장치가 6개로 늘어 상황 인식(가장 위험한 장치 기준)·Safety Guard 거부·자동 차단·응답 문장·시뮬레이터 시나리오·Unity 온도 보고(HW-19)가 모두 새 장치를 다룬다. 기존 시나리오 26개의 정답은 바뀌지 않는다 (새 장치는 꺼져 있음).
- 전자레인지에 270°C 목표 온도는 실제와 다르다 — 시연용 단순화로 두고, 시연에서 어색하면 장치별 목표 온도를 따로 정한다.
- 영향: [interfaces](../architecture/interfaces.md) §2.2·§3·§4, `common/function_call.py`·`common/kitchen_link.py`, `services/llm_svc`(규칙 파서·`stt_fixes`), `services/audio_svc/responses.py`, `services/safety_guard`, `services/fusion_svc`, `services/simulator`, Unity `KitchenLink`, LLM 데이터·학습([recipe](../../recipes/llm-to-rkllm.md)), [PLAN](../PLAN.md) LLM-20

- 전자레인지·오븐 온도 규칙이 시연에서 어색할 때
